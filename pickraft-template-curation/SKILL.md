# Pickraft 模板治理

用于对 Pickraft 模板进行可追踪的批量审查和最小修改。每个模板都必须经过“读取 → 判断 → 生成或选择素材 → 更新 → 回读 → 记录”闭环；不能只根据数据库写入成功就宣称完成。

## 适用范围

- 缺少必填输入示例的模板
- 输入示例过度风格化、无法代表普通用户上传照片的模板
- prompt 固定画幅、参数占位符、主体适配规则或多人描述不清的模板
- category、styles、tags 与模板用途明显不一致的模板
- 需要人物、多人、宠物、风景或建筑输入的模板

不把真实用户照片、个人资料、访问令牌、云端密钥、内部本机路径或线上导出的完整数据写入 Skill 仓库。

## 核心判定

### 输入示例缺失

仅当以下条件同时满足时，模板才算缺少输入示例：

1. 存在至少一个 `inputRequirements[].required === true`；
2. `examples` 不存在、为空，或所有 `examples[].inputs` 都为空。

只有输出示例不算输入示例。线上详情接口回读时，必须确认输入 URL/preview URL 可用，并保留 `inputs` 与 `outputs` 数量证据。

### 输入示例质量

输入示例是“用户上传什么样的照片”，不是模板输出的成片预览。默认使用：

- 虚构的成年人物，不对应现实人物；
- 日常服装、自然发型、淡妆或无明显妆容；
- 简洁室内、浅色墙面或普通生活环境；
- 自然站立、轻微侧身或普通抓拍；
- 半身或能清楚识别人物的常规构图；
- 无品牌、无文字、无水印、无强烈滤镜。

默认禁止把模板的特殊服装、道具、场景、妆造、电影灯光、复杂动作和输出构图复制到输入示例中。只有当 `inputRequirements` 明确要求全身、多人、宠物或特定物体时，才加入对应内容。

### 多人模板

如果模板明确需要情侣、双人或群像合照：

- 示例使用自然合照，人物身份清楚、关系自然，不做杂志式摆拍；
- 检查 prompt 是否写明“以上传照片中的每个人为主体并保留各自身份”；
- 记录 `multi-person-template-followup`，说明当前是否已经支持动态适配；
- 未经明确验证，不把单人模板直接改成多人模板，也不删除原有多人要求。

### 风景和建筑模板

优先使用许可证明确、可商用且能追溯来源的公开素材。记录来源 URL、作者、许可证、下载时间和本地文件校验信息。无法确认授权时，使用抽象或生成的无版权风险素材，并在审计中标明来源，不把来源不明的网络图片上传为示例。

## 标准工作流

## 用户反馈驱动的逐模板处理

当用户要求“按反馈逐个排查”时，必须串行处理，不能批量修改后一次性汇报：

1. 按反馈创建时间顺序取下一条反馈，读取模板当前线上详情、Prompt、参数、输入要求和现有示例；
2. 只处理当前模板，先不要处理下一条反馈；
3. 根据反馈生成候选输入图，并用当前模板 Prompt、实际参数和该输入图跑一次真实生成；
4. 将输入图和输出图合成为左右对照图展示给用户，同时说明本次拟修改的参数、Prompt、分类或标签；
5. 在用户确认前，不替换线上示例、不提交模板修改、不继续下一个模板；
6. 用户确认后，再上传输入图和输出图，提交线上模板并回读 `status=200`、`inputs=1`、`outputs=1`；
7. 记录用户确认、最终文件 ID、参数值和审计记录，然后再取下一条反馈。

### 参数处理规则

- 删除反馈明确指出“没有作用”的参数，不为了保留数量而保留参数；
- 参数名称、`example`、`placeholder`、`suggestions[].value` 和 Prompt 占位符必须一致；
- 用户可直接理解的参数优先使用中文示例，例如颜色使用“米白色”，不要只展示 `vibrant green (#2E7D32)` 这类内部或英文描述；
- 数字参数使用纯数字示例，例如球衣号码使用 `7`，不要使用 `number 7`；
- 用于验证输出的参数值必须与线上默认示例一致，不能测试时手动使用另一组值；
- 删除或修改参数时同步检查 Prompt 中残留的性别、姓名、服装、发型和其他固定描述；
- 反馈要求取消性别限制时，同时检查模板名称、默认参数、Prompt 中的 `female/male`、`she/he`、性别专属发型和服装描述，不能只改参数名称。

### 确认前后的提交边界

候选图和测试输出可以保存在本地临时目录，但不应在用户确认前写入线上模板。确认后才执行：

- 上传输入图和输出图；
- 替换或追加 `examples[0].inputs` 和 `examples[0].outputs`；
- 写入 `template-feedback-resolution` 审计；
- 回读线上详情并报告结果。

如果用户只确认了参数或 Prompt，但没有确认输入/输出图，仍不能提交示例图；如果用户确认图和修改方案，则一次性提交当前模板的全部已确认变更。

### 输入图复用与复核收尾

- 修复或发布前，按稳定的输入文件 ID；没有文件 ID 时使用 SHA-256，检查当前模板每个示例输入是否已被其他公开模板复用。若发现复用，为当前模板重新生成合规输入照片，并替换当前模板所有受影响示例的输入/输出配对、封面关联、参数绑定和审核记录；不要只替换单张或伪造配对。其他模板的既有公开素材不因本次检查自动改动。
- 用户确认模板无问题后，删除仅用于本次复核的本地临时预览目录或文件；保留来源、提示词、审核记录、正式样片和必要的追溯材料。删除前确认线上公开素材已验证，不把本地预览当成发布资产。
- 需要微信页面级验收时使用仓库内 `pickraft-wechat-acceptance` skill；模板治理 skill 负责模板内容和公开数据核验，不复制微信验收脚本、用例或真机边界。

### 1. 获取实时清单

不要只依赖旧 CSV。重新读取线上或数据库中的模板，按启用、上架、必填输入要求和实际 `examples[].inputs` 过滤。批次建议为 5 个，避免生成、上传和回读难以核对。

每批先记录：

- 模板 ID、短 ID、名称；
- category、styles、tags；
- inputRequirements 及 required role；
- prompt 中的固定比例、参数占位符和多人描述；
- 是否属于人物、多人、宠物、风景或建筑输入。

### 2. 审查 prompt、比例和参数

检查以下问题：

- 是否有“上传照片身份优先”的规则；
- 是否把示例人物的姓名、族裔、脸型或性别强加给用户；
- 是否固定 `3:4`、`9:16` 等比例而没有必要；
- 是否把比例写死在 prompt，同时又有可选输出比例；
- `{argument name="..." default="..."}` 是否有清晰默认值和安全范围；
- 是否把多人、宠物或场景要求写成可执行的主体规则；
- 是否有品牌、名人、受版权保护角色或无法稳定生成的要求。

只做有明确依据的最小修改。prompt 变更必须记录旧值摘要、新值摘要、原因和验证结果。

### 3. 生成或选择输入素材

人物示例的生成提示词应明确包含：

```text
虚构成年东亚人物，仅作为用户输入参考；普通日常服装；自然表情；
简洁背景；真实手机或生活摄影；无品牌、无文字、无水印；
不对应任何现实人物；不要复刻模板输出的特殊造型、道具或场景。
```

根据 `inputRequirements` 决定单人、自然合照、宠物同框或物体/场景参考。不要为了匹配输出示例而过度装扮输入人物。

### 4. 用真实模板链路验证输入

生成输入示例后，不能只看输入图本身，也不能直接把图片写入模板就结束。必须调用当前环境可用的本地图像生成 Skill，使用该模板的实际 prompt、参数和新生成的输入图跑一次真实生成链路。

验证时检查：

- 输出是否保留输入人物的身份特征，而不是被输入示例的虚构人物替换；
- 输出是否体现模板 prompt 的主题、服装、动作、场景和风格；
- 输出比例、主体位置和裁切是否符合模板预期；
- 多人模板是否保留每个人、人数和关系；
- 是否出现手部、脸部、文字、品牌、道具或场景异常；
- 输入示例是否过度影响输出，或反过来无法承载模板要求。

需要迭代时按以下顺序处理：

1. 先调整输入示例，使其回到普通、清晰、可识别的用户照片；
2. 输入图合格但输出不符合主题时，再最小修改 prompt；
3. prompt 修改后重新调用本地图像生成 Skill；
4. 保存输入图、实际 prompt、参数、输出图和检查结论之间的对应关系；
5. 只有通过视觉检查后，才把输入示例写入线上模板。

本地生成 Skill 的名称、参数和输出目录由当前环境决定，不在本 Skill 中硬编码具体实现、模型密钥或本机路径。若本地图像生成 Skill 不可用，应停止该模板的线上更新并明确记录阻塞原因。

### 5. 上传和更新

素材上传路径建议使用：

```text
template-input-examples/{templateId}/{descriptive-file-name}.png
```

更新时只追加或替换目标示例的 `inputs`，保留已有 `outputs` 和未涉及字段。写入必须是事务性的，并在同一流程写入审计记录。审计至少包含：

- action：`append-generated-example`、`replace-low-quality-example`、`taxonomy`、`prompt-review` 或 `multi-person-followup`；
- templateId、role、fileId；
- 素材来源和生成模型（如适用）；
- 修改原因、时间和操作者。

### 6. 线上回读

对每个模板请求线上详情接口，确认：

```text
status=200
examples[0].inputs.length >= 1
examples[0].outputs.length >= 1（原本存在时）
category/styles/tags 与本次审查结果一致
parameters 数量和占位符审查结果一致
```

如果模板已下架或接口返回 404，回读结果应标记为下架，不把数据库写入冒充为线上公开完成。

### 7. 统计和交付

重新计算剩余缺失数量，并输出：

- 本批处理模板及名称；
- 输入素材来源和文件 ID；
- prompt、比例、参数、分类和标签变更；
- 实际模板生成验证的输入图、输出图、视觉结论和迭代次数；
- 多人适配记录；
- 每个模板的线上回读证据；
- 当前剩余缺失数量。

## 质量门

提交前逐项检查：

- 示例图是否像普通用户会上传的照片；
- 是否已经用真实模板 prompt 和输入图跑过一次本地生成链路；
- 生成输出是否符合模板预期，且视觉检查结论可追溯；
- 是否存在过度造型、强场景、道具、文字或品牌；
- 人物是否为虚构成年人且不对应现实人物；
- 多人数量、宠物和输入角色是否与要求一致；
- 素材来源是否可追溯且可商用；
- prompt 是否身份优先、比例不过度写死、参数可解释；
- category、styles、tags 是否与模板用途匹配；
- 更新后是否完成线上详情回读；
- 审计文件是否不含密钥、私人照片和本机私有路径。

发现不合格示例时，先替换示例图再继续下一批；不要把“已上传”当作“质量合格”。
