# 淘宝订单开票

把已购订单整理为可核对的开票清单，再通过 Ego 完成申请和商家沟通。依赖已安装的 `ego-browser` skill、可用的 Ego 浏览器及用户的淘宝登录状态；操作浏览器前读取该 skill，遵循其当前 API 和空间控制规则。缺失依赖时说明缺项，不改用另一个账号或浏览器静默执行。

## 1. 先确定商品范围

先从当前对话提取用户已确定的条件，只询问缺失项，不重复确认已经授权的内容：

- 商品关键词、类目、店铺或指定订单；可沿用用户当前搜索，但实际筛选条件仍需核实。
- 起止日期，以及使用下单时间还是成交时间。把“今年”“2021年以来”等转换为明确日期范围。
- 金额下限与边界：如“超过50元”是 `>50`，“50元及以上”是 `>=50`；说明按订单实付还是商品实付筛选。
- 交易状态、退款和售后排除规则。“没有发生售后”应排除曾发起后又取消的售后；若只排除实际退款则按该口径处理。
- 是否只补开尚未开票的订单；默认避免重复申请，状态不明时先核实。

浏览订单可与澄清并行，但范围未确定前不发送开票请求、不提交申请。不把历史任务的关键词、年份或金额门槛当作所有用户的固定规则。

## 2. 确认开票与执行方案

在发消息或提交申请前，汇总一份简短方案。信息已完整且用户已明确授权执行时，直接沿用；否则一次性补齐关键项：

| 项目 | 需要确定的内容 |
| --- | --- |
| 抬头 | 个人或单位、准确名称；单位开票所需税号 |
| 类型与内容 | 所需电子/纸质、普通/专用发票；按实际购买商品与金额开具 |
| 合并 | 同店多笔是否允许合并；合并不支持时是否接受分开；默认不跨商家合并 |
| 收票要求 | “开具即可”还是需要文件；邮箱仅在用户要求或申请表必填时提供 |
| 执行范围 | 直接处理全部，或先试指定数量商家后等待确认 |
| 跟进规则 | 是否跟进回复、清除已结束会话未读，以及确实无法开具时如何结束 |

推荐方案为：优先平台直接申请，缺少入口再联系商家；同店允许合并时只合并确认未开具的订单；电子发票确认已开即可完成，不主动索要文件或邮箱投递；确实无法开具则礼貌致谢结束。以用户的明确选择为准。

不要把此 skill 的加载当作发送消息的授权。用户确认的执行方案可以覆盖相应批次的发送、申请和必要跟进，无需逐条再问。仅要求查询进度时不要自行新增开票批次。用户设置“先两家”时，完成试点就停止扩展，报告结果后等待确认。

## 3. 在 Ego 核对并执行

1. 找到用户指定的淘宝空间，使用同一个 TaskSpace 续做，不硬编码空间编号、页面标签、DOM ref 或历史聊天 URL。查看现有标签再复用订单页与聊天页。
2. 从页面逐项核对日期、商品、实付、交易状态、售后和开票状态。分页检查到范围边界，不能因搜索结果还在加载或当前页为空就断言处理完毕。无法核实的订单单独标记，不能冒充符合条件。
3. 按商家分组，记录订单号和实付；将已开、已申请、待核实订单分开。合并金额只计算本次纳入且未开具的订单，不把店铺全部历史消费求和。
4. 优先检查订单的“申请开票”等真实入口。提交前核对关联订单、抬头、税号、内容和金额，提交后读取成功状态；只有点击按钮不算申请成功。
5. 没有直接入口时发送简洁请求。合并可行则附订单明细和合计，超过聊天字数限制时拆成有编号的消息，避免遗漏或重复订单。
6. 商家发来申请卡片时自行打开填写。若没有可选发票类型或入口不可用，如实说明并请求人工按实际交易开具，不随便选择其他订单或不符类型来绕过。

可用话术，替换占位符后发送：

> 您好，想麻烦补开以下订单的发票。抬头：{抬头}；税号：{税号}。订单：{订单号及实付}。如尚未开具，麻烦按实际购买商品开具{发票类型}，谢谢您！

允许合并时补充：

> 这几笔未开票订单合计{金额}元，方便的话可以合并开一张，分开开具也可以，辛苦您了！

没有可选类型时：

> 您好，我打开申请入口后没有可选的发票类型，暂时无法提交。麻烦帮忙看看能否人工按这笔实际交易开具，感谢您！

## 4. 根据回复推进

阅读上下文后再决定动作，不仅根据列表摘要或关键词自动回复。

| 商家回复或页面结果 | 动作 |
| --- | --- |
| 要求订单号、抬头、税号 | 从已确认清单补充，避免让用户重复提供 |
| 要求邮箱等必填信息 | 复用本次已授权信息；缺失时只问所缺字段，不编造 |
| 已登记、转财务、预计几天 | 记录待开具与承诺时间，不能记成已开；未到期不连续催 |
| 明天再联系 | 记下明确日期；用户下次要求跟进时按日期检查，不擅自建立定时任务 |
| 已开好了、已发送电子发票 | 若约定“开具即可”，记为“商家确认已开具”，不索取文件，也不声称核验过文件内容 |
| 发来文件，或用户要求核验 | 核对抬头、税号、金额和订单归属；只在用户需要时保存，不自动扩大到邮箱搜索 |
| 金额不符、仅定金、疑似重复收据 | 核实订单、子订单、定金尾款和优惠，不直接认定错误；说明具体差异，请商家核对 |
| 确实无法开具 | 礼貌回复“好的，了解了，谢谢您，辛苦了！”并结束，不持续施压 |
| 提议无关消费或不实金额发票 | 不接受替代；请求按真实交易处理，无法开具则礼貌结束 |
| 表情、收到、谢谢等结束语 | 不追加无意义回复；按用户要求点开清除未读 |

进口商品可能提供境外收据。区分境外收据与国内发票，不能把“收据已出”描述为“国内发票已开”；是否接受收据沿用用户选择，未明确且影响目标时询问。

## 5. 可靠续做与结果记录

在用户允许的本地任务目录维护最小进度清单，放在公开 skill 仓库之外。每笔记录商家、订单号、日期、实付、筛选结论、开票状态、最近动作和时间、下一步；合并申请额外记录所含订单与合计。涉及个人信息只保存必要字段。

建议区分：待核实、符合条件待申请、已申请待开、商家确认已开、文件已核验、无法开具已结束、范围外、操作受阻。记录状态的依据，商家承诺不等于实际开具。

- 续做时先读进度，再检查当前页面；过期记录不能代替实时状态。
- 发送后读取聊天历史，确认内容与目标店铺正确；提交后检查结果。如果发送结果不确定，先查历史，不能直接重发。
- 页面切换或异步加载后重新观察。旧 ref 不跨页面复用；聊天里的订单卡必须核对订单归属。
- 验证码、浏览器权限提示或用户接管时，按 `ego-browser` 交还控制，等待用户处理，不绕过验证。
- 无法联系、被拉黑、店铺关闭分别记录，不解除黑名单，不发起投诉或售后作为催票手段。
- 一轮完成后按 Ego 生命周期规则处理空间；需用户继续查看或操作时保留必要页面。输出已处理、待处理及真正需要用户动作的事项，不宣称未遍历的订单全部完成。

公开发布 skill 时只保留通用流程和占位符，不包含真实抬头、税号、邮箱、订单、聊天截图、发票、登录状态或本机私有路径。
